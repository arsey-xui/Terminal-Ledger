> 但它按「通用产品」分层，范围取舍不适合「个人单用户、三端由一个人维护」的实际情况，所以这里重排了优先级：

### 1. 补 `sql/init.sql` 的 `recurring_rule` 建表

- [x] 完成

- **规模**：小 · 无依赖
- **现状**：v1.2.0 加了周期记账，`RecurringRule.java` 有实体、`RecurringRuleRepository` 有查询，但 `sql/init.sql`
  只有 `accounts` / `category` / `transaction_record` / `budget` / `template` 五张表。MySQL profile 是
  `ddl-auto: ${JPA_DDL_AUTO:none}`，所以按 README 用 `init.sql` 建的库，任何拉到周期规则的同步都会报表不存在。
  开发 profile（H2）是 `ddl-auto: update`，所以本地永远看不到这个问题。
- **改动**：`sql/init.sql` 补建表（列对齐实体：`client_id` 唯一键、`name`、`amount`、**`txn_type`**（实体里
  `type` 映射到的列名就是它，别写成 `type`）、
  `category_client_id`、`account_client_id`、`note`、`interval_unit`、`interval_count`、`anchor_date`、
  `last_generated_date`、`enabled`、`sort_order`、`last_modified` + 索引、`deleted`、`created_at`、`updated_at`）；
  另加 `sql/upgrade-recurring-rule.sql`（`CREATE TABLE IF NOT EXISTS`，可重复执行），给已经建好的库补这张表。
- **验收**：全新 MySQL 按 README 初始化后，一次 push + pull 不报错。
- **验证**（已做）：在 H2 的 MySQL 兼容模式下用 `sql/init.sql` 建库（剥掉 `CREATE DATABASE`/`USE` 这类
  库级语句，表结构与示例数据全保留），后端以 `ddl-auto=none` 连上去跑一次 pull + push ——
  返回 `accounts=5 categories=13 budgets=2 templates=2`，周期规则查询正常，push 无异常；
  另外用脚本把实体注解推导出的 18 个列名与两份 DDL 逐列比对，集合完全一致。
  真 MySQL 上的端到端还没跑（本机 Docker 守护进程未启动），需要时可用 `docker compose up -d` 复核。

### 2. 拉取窗口只作用于流水，字典实体全量

- [x] 完成

- **规模**：小 · 无依赖
- **现状**：`SyncServiceImpl` 在 `since == 0` 时把 `since` 改写成 90 天前，同一个 `since` 又被 `listChanges`
  用在六张表上。于是几个月前创建、之后没改过的分类/账户，新设备永远拉不到，流水的外键就悬空了。
- **改动**：窗口只对 `transaction_record` 生效；分类、账户、模板、周期规则、**预算**一律 `since = 0`。
- **已定**：预算按字典处理（每次都全量拉）。条数少（每个分类每月一条），跨月预算否则拉不到。
- **验收**：新设备首次同步能拿到三个月以前创建、之后没修改过的分类与预算。
- **验证**（已做）：同一份由 `init.sql` 建出来的库上，`init.sql` 示例数据的 `last_modified` 是 2025-06
  （早已在 90 天窗口外）。旧逻辑下这次 pull 返回 `accounts=0 categories=0`；
  改动后返回 `accounts=5 categories=13 budgets=2 templates=2`，而流水仍是 `transactions=0`（窗口按设计生效）。
  这一对数字就是本条的 before/after。

### 3. 桌面端 `Template` 补 LWW 比较

- [x] 完成

- **规模**：小 · 无依赖
- **现状**：`desktop/src/main/java/com/personal/accounting/desktop/sync/SyncManager.java` 里
  `lww(Template)` 直接 `db.upsertTemplate(t)` 并返回 true，其它实体都有 `ex.lastModified > t.lastModified`
  的比较。远端较旧的模板会覆盖本地较新的。
- **改动**：`DataManager` 新增 `findTemplate(clientId)`（含软删除墓碑，不要过滤 `deleted`）；
  `lww(Template)` 与 `lww(Transaction)` 等对齐。
- **验收**：两端各改同一个模板，`lastModified` 较早的一方不会胜出。
- **验证**（已做）：反射调用真实的 `lww(Template)` 跑了三组 —— 远端更旧 → 拒绝且本地内容不变；
  远端更新 → 接受；软删除墓碑仍能被 `findTemplate` 查到。把旧实现放回副本再跑，
  同一个检查失败在「远端较旧的模板被合并了」，说明它确实能抓到该缺陷。桌面端 26 个测试全过。
- **未覆盖**：`created_at`/`updated_at` 在桌面端多数 upsert 里就是统一的 `null`（category/budget/
  recurring_rule 都如此），不是 Template 特有的疏漏，所以没动；要不要统一改成持久化属于另一件事。

### 4. 同步游标不混用 ID 空间

- [x] 完成

- **规模**：中 · 第 1–3 之后
- **现状**：游标是 `(lastModified, id)`，其中 `id` 取自 `txns.get(last).getId()`，却被当成六张表共用的
  `sinceId` 传给各自的 keyset 查询。而 `id` 是各表自己的自增序列，于是「本页只有分类、流水没满页」时
  游标会停在原地（无限重复同一页），id 大小对不上时还会跳过记录。
- **改动**：新增 `SyncCursor`（六个实体各自一对 `(lastModified, id)`），`listChanges` 按各自的段查询；
  满页的段接在最后一条之后，没满页的段钉成 `(Long.MAX_VALUE, Long.MAX_VALUE)` 表示「已取完」。
  游标编码改为 6 段 `ts:id` 的 Base64；`decodeCursor` 兼容旧的单段格式（按旧语义铺到六段上）。
  `pullWindow` 一并迁到新游标。删掉不再需要的 `maxLastModified`。
- **两端无需改动**：客户端一直把 `nextCursor` 当不透明字符串透传（手机端 `pullReq.cursor = resp.nextCursor`，
  桌面端 `pull.cursor = resp.nextCursor`），编码格式变化对它们不可见。
- **验收**：构造「本页只有分类、没有流水」的场景，连续翻页不丢记录、不卡住。
- **验证**（已做）：5 个分类 + 2 条流水、同一个 `lastModified`、页大小压到 2（分类要 3 页、流水 1 页取完）。
  新实现 3 页收敛，5 个分类 + 2 条流水各出现一次；把旧实现换回副本再跑同一个测试，
  它卡满 20 页上限后失败：`cat-5` 从未返回、`cat-3`/`cat-4` 每页重复（游标原地打转）。
  后端 19 个测试全过。

### 5. 写入类操作后触发同步

- [x] 完成

- **规模**：中 · 建议与第 6 点合并做
- **现状**：手机端删除流水（`HistoryFragment` 的删除按钮）、保存/重置预算（`BudgetFragment`）、
  删除分类或账户（`SettingsFragment`）都只写本地，不触发同步。
- **为什么不是打磨项**：删除的墓碑只留在本机，另一端下次拉取仍会拿到那条活记录；桌面端再编辑一次，
  这条被删的记录就复活了，两端状态永久不一致。这属于数据正确性。
- **改动**：上述写入点之后触发一次同步；桌面端对应的删除与保存同样处理。
- **验收**：手机删一条 → 立即同步 → 桌面端拉取后那条消失。
- **实际改动**：
  - 手机端加 `SyncManager.requestAfterWrite()`：静态入口 + 1.2 秒去抖（一次操作连写多行时只同步一次），
    没配后端地址时直接跳过。同步仍跑在原有的单线程 executor 上，所以不会并发写库。
  - 覆盖 14 个写入点：`HistoryFragment` 删除流水；`BudgetFragment` 保存/重置预算；
    `RecordFragment` 新增分类/账户（记账保存本来就直接同步）；`SettingsFragment` 的
    重置分类/账户/预算（经共用回调 `confirmReset`）、删除分类/账户/周期规则（经共用回调
    `confirmDelete`）、周期记账的两个确认入账、新建/编辑规则。
  - 桌面端加 `syncInBackground()`（原重置流程里那段内联静默同步抽出来复用），
    接到删除/新增账户、保存预算、删除周期规则四个点。
  - 重置弹窗文案从「会在下次同步时同步到云端」改成「会立即同步到云端」。
- **验证**：两端编译通过、桌面端 26 个测试全过；逐条比对写入点与触发点，14 处写入点全部有触发
  （4 处直接插入、9 处经两个共用回调覆盖、1 处记账保存原有直接同步）。
  **去抖与「写入后 1.2 秒真的发起同步」这条时序没有自动化验证**——它需要 Android 运行时
  （Robolectric 或真机），属于第 9 点的范围；目前只有代码层面的证据。
- **与第 6 点的关系**：本点让「删除也同步」，而两端 push 仍是全量。在没做第 6 点之前，
  每次删除都会触发一次全量上传；数据量小的时候无感，账本变大后会被这一条放大。
  第 6 点（增量水位）做了之后才是最终形态。

### 6. 增量同步水位（两端 push/pull）

- [x] 完成

- **规模**：大 · 第 5 点的前置
- **现状**：两端 pull 都硬编 `since = 0`；push 是 `listModifiedSince(0)`——**每次保存一笔账，都把整本账
  上传一遍**。手机端已经有 `sync_state.last_sync` 表和「上次同步于 X 分钟前」的展示，桌面端还没有水位存储。
- **改动**：
  - push 只推 `listModifiedSince(水位)` 的记录；
  - pull 用 `last_sync` 作为 `since`；
  - 保留「首次 / 换设备」的全量拉取路径（水位为 0）；
  - 桌面端新增水位存储（H2 表或配置文件）。
- **为什么先做这个**：没有水位时加自动同步（第 5 点），等于把全量上传从「每次保存」放大到
  「每次删除、每次切网」。
- **验收**：保存一笔后，push 的体量从「全量」降到「1 条 + 字典差异」；换设备仍能完整还原历史。
- **实际改动**：两端各存**两个**水位，因为它们是两个时钟域，不能共用一个值：
  - `last_sync`：pull 水位，存服务端 `serverTime`（用**第一页**的，最保守）；
  - `push_watermark`：push 水位，存本机 `last_modified` 的最大值。
  手机端 `sync_state` 由 3 版升到 4 版，用 `ALTER TABLE ... ADD COLUMN` 增量加列（不重建库）；
  桌面端在 `DataManager` 的建表处加 `ADD COLUMN IF NOT EXISTS`，老库自动补齐。
  两端都改成「先 UPDATE、没有行再 INSERT」：**不能用 `CONFLICT_REPLACE` / 省略列的 MERGE**，
  那会把另一列清成默认值，等于两个水位互相清零。
  水位规则：pull 取 `stored - 1h`（容忍服务端 `last_modified` 与 `serverTime` 的时钟差），
  push 取 `min(stored, now - 1h)`（最近一小时的改动总是重推，时钟回跳也不漏），
  水位本身精确推进；只在整轮成功后落盘。同步结果文案改成「上传 N 条，合并 M 条」。
- **验证**（已做）：桌面端用 JDK 自带的 `HttpServer` 做桩，驱动**真实的** `SyncManager` 连续同步三轮。
  预置 5 条两小时前的记录：第一次推 5 条，**第二次推 0 条**，改一条之后**只推那 1 条**；
  `pull` 带上去的 `since` 从 `0` 推进到服务端水位；两个水位都落盘且互不覆盖。
  桌面端 26 个测试全过，手机端编译通过。
- **仍未覆盖**：换设备时 `since=0` 只拉最近 90 天流水（字典类是全量）。更早的历史要靠后端的
  `pull-window` 回补，而**两端目前都没有调用它** —— 这是本次之前就存在的缺口，不是水位引入的。
  要补的话是在两端各加一个「拉取更早历史」的入口驱动 `pull-window` 分页。
- **另一处已知限制**：服务端的 `last_modified` 由各客户端时钟写入，而 `since` 是服务端 `serverTime`。
  一台设备的时钟明显落后时，它写入的记录对其它设备可能落进「已同步」区间。1 小时重叠只能容忍
  小幅偏差；要根治得让服务端统一签发时间戳，那是协议层的改动。

### 7. 版本可追溯

- [x] 完成

- **规模**：小 · 无依赖
- **现状**：`android/app/build.gradle` 是 `versionCode 5` / `versionName "1.3.0"`，而同一个 `versionCode`
  已经被多个行为不同的构建用过——装到手机上分不出装的是哪一个。

  设置页版本行显示 `versionName + versionCode + 构建时间`；桌面端显示同样的信息。
- **验收**：先后装两个构建，设置页能直接分辨。
- **实际改动**：
  - 出包：`scripts/build-android-release.ps1` 每次出包把 `app/build.gradle` 的 `versionCode` 自增
    （`-NoBump` 用于原样重打），产物文件名带上构建号：`TerminalLedger-<版本>-b<code>-arm64-v8a.apk`；
  - 手机端：`build.gradle` 开启 `buildConfig` 并注入 `BUILD_TIME`、`GIT_COMMIT`；
    设置页版本行显示「当前版本：1.3.0 (6)」换行「构建：2026-10-18 22:14 · 提交号」；
  - 桌面端：`desktop/pom.xml` 把 `build.time` / `git.commit` 写进 fat jar 清单（`Built-At` / `Git-Commit`），
    新增 `service/BuildInfo` 读取它们，左下角显示 `v1.3.0 · 2026-10-18 22:16 · fe5b656`（标签已开换行）；
    打包脚本取**本地时间**与 `git rev-parse --short HEAD` 传给 Maven —— 直接 `mvn package` 时
    `build.time` 会退化成 Maven 自带的 UTC 时间戳、提交号为空，所以正式出包要走脚本。
  - `versionName` 仍是 1.3.0：本批是 v1.4.0 的进行中状态，版本名等清单做完再改；
    现在区分构建靠 `versionCode` + 构建时间 + 提交号。
- **验证**（已做）：跑真实打包脚本，日志 `versionCode: 5 -> 6`；APK 的 `aapt2 dump badging` 显示
  `versionCode='6' versionName='1.3.0'`；dex 里能查到 `BUILD_TIME` / `GIT_COMMIT` 字段与构建时间字符串。
  桌面端用打好的 fat jar 跑 `BuildInfo.summary()`，输出 `v1.3.0 · 2026-10-18 22:16 · fe5b656`；
  重打的 app-image 内 jar 清单含 `Built-At: 2026-10-18 22:16` 与 `Git-Commit: fe5b656`。
  桌面端 26 个测试全过。
- **未覆盖**：两处的字面效果没法在这里看 —— 手机端要真机，桌面端开窗口会读写真实的 `~/accounting`。

### 13. 账户余额与净资产

- [x] 完成

- **规模**：中 · 无依赖
- **现状**：`initial_balance` 在三端都有列、会存取、会同步，但没有任何地方计算或显示余额。
- **改动**：`余额 = initial_balance + Σ收入 − Σ支出`（排除已删除，按 `date <= 今天`）；手机端在账户卡片或
  报表页顶部显示，桌面端在仪表盘显示。
- **验收**：口径写在实现处的注释里，两端同一份数据算出同样的数字。
- **口径**（写在两端 `AccountBalance` 类的注释里）：
  - 只算未删除的流水，且日期不晚于今天。
  - 单账户余额 = 账户初始余额 + 该账户名下流水收入 − 支出。
  - 净资产 = 各未删除账户初始余额之和 + 全部流水收入 − 支出。
  - 净资产刻意不依赖「流水挂在哪个账户」：初始余额之和加全部流水，与逐账户求和再相加恒等，
    即使有流水指向已删除的账户也一样。两端因此必然算出同一个数。
- **实际改动**：
  - 两端各新增一个纯口径类：手机 `analysis/AccountBalance.java`（`double`），
    桌面 `service/AccountBalance.java`（`BigDecimal` + HALF_UP 两位小数），各配 5 个单元测试。
  - 手机端取数：`TransactionRepo.flowByAccount(today)` 用一条 SQL 按 `account_client_id + type` 聚合
    （`deleted=0 AND date<=today`），账户为空的流水归到 key `""`。
  - 手机端展示：报表页顶部新增「净资产 ¥…」一行（`money_net_worth`）；
    设置里「管理账户」弹窗的标题带净资产，每个账户条目显示自己的余额。
  - 桌面端取数：`db.listAccounts()` + `db.listTransactions(1970-01-01, 今天)`，在 Java 里按
    `counts()` 过滤后累加。
  - 桌面端展示：仪表盘「结余」卡片旁边新增「净资产」卡片（`labelNetWorth`）。
- **验证**（已做）：两端编译通过；Android 15 个测试全过（含新增 5 个），桌面端 31 个全过（含新增 5 个）。
  其中 `netWorthEqualsSumOfAccountBalances` 专门钉住「净资产 = 逐账户余额之和 + 未归属流水」这个恒等式。
- **注意**：「结余」和「净资产」是两个口径——前者只看本月收支，后者是全期含初始余额，两个都留在界面上。
- **没做的**：桌面端没有把每个账户的余额单独列出来（只有手机端的账户管理弹窗里逐账户显示）。

### 16. 共享密钥鉴权（后端 + 两端）

- [x] 完成

- **规模**：中 · **最后做，且必须留过渡**
- **现状**：后端没有任何 Filter / Interceptor / Spring Security 配置，所有 `/api/**` 匿名可访问；
  而手机是通过 Wi-Fi 连后端的，同一局域网内的人可以读写账本。`application.yml` 里有
  `accounting.sync.token.secret`，但 `SyncProperties` 只有 `pullWindowMonths` / `pullPageSize` 两个字段，
  这个 secret 连绑定都没有。
- **改动**：后端加一个 `OncePerRequestFilter` 校验共享密钥，放行 `/api/health`；把 token 绑进 `SyncProperties`；
  两端设置页加 token 输入并随请求带上。
- **必须注意**：未配置 token 时**不校验**，否则升级瞬间旧客户端全部 401。
- **验收**：未配置 token 时行为不变；配置后无 token / 错误 token 返回 401，正确 token 正常。
- **实际改动**：
  - 后端：`SyncProperties` 加 `sharedSecret`（`accounting.sync.shared-secret`，默认取 `SYNC_SHARED_SECRET`）；
    新增 `SyncTokenFilter`（`OncePerRequestFilter`）校验请求头 `X-Sync-Token`。留空不校验，`/api/health` 永远放行；
    比较用 `MessageDigest.isEqual`（定长比较，不从前缀匹配长度泄漏信息）；失败返回 401 +
    与其它接口同形的 `{success:false,message,data}`。
  - 手机端：`SyncConfig` 加 `TOKEN` 与 SharedPreferences 持久化（`sync_token`），`MainActivity` 启动时读回；
    `ApiClient.post/get` 带上 `X-Sync-Token`。**`getAbsolute` 不带** —— 它打的是 GitHub 之类的外部地址，
    把密钥带出去等于主动泄露。设置页原来的「保存地址」改成「后端连接」弹窗，地址与密钥一起填。
  - 桌面端：`SyncConfig` 加 `TOKEN` 写进同一个 `sync.properties`（`token` 键；写时保留 `base_url`，
    且 `saveBaseUrl` 会把已有 token 写回去，两者不会互相冲掉）；`ApiClient` 用 OkHttp 拦截器统一加头
    （桌面端所有请求都指向自家后端）；「数据管理」的设置区加了密钥输入框。
- **升级顺序**（原计划里的硬要求）：密钥留空 = 不校验，所以必须
  ① 先部署新版后端（不配密钥，行为完全不变）→ ② 两端更新并各自填上密钥 → ③ 最后才给后端配
  `SYNC_SHARED_SECRET`。顺序反了会在配密钥那一刻把旧客户端全部挡成 401。
- **验证**（已做）：后端 24 个测试全过（新增 5 个：留空放行 / 缺 token 401 / 错 token 401 /
  正确放行 / 健康检查免检）；Android 15 个全过；桌面端 31 个全过；三端编译通过。
- **连带影响**：`/api/version` 也在 `/api/**` 下，配了密钥后同样要求 token —— 新版客户端的「检查更新」
  会带密钥所以正常，**旧客户端**的检查更新会 401。计划里只要求放行 `/api/health`，这里按计划做。

## 依赖与建议批次

- **第一批 = 1–9**（同步与基础设施）：不新增界面，风险低、可回归，是后面所有同步功能的地基。
  内部顺序：1–4（后端同步修正）→ 5（写入后同步）→ 6（增量水位）；7–9 与它们无依赖，可并行。
- **第二批 = 10–16**（功能与安全）：10–14 相互独立，15 只需一个决定，16 最后做。
- **5 与 6 必须合并做**：只加自动同步而不做水位，会把全量上传放大到每次删除、每次切网。

## 不在本期范围

| 项 | 为什么不进 v1.4.0 |
| --- | --- |
| 转账（`TRANSFER` 类型） | 三端 schema + 报表 + 预算排除，是最大的一项；它是数据模型缺口（当前信用卡还款记成「支出+收入」会虚增两边），值得做成 v1.5 的主打 |
| 周期记账的结束条件 | 三端加列 + 同步 + UI，换掉的是「车贷记 36 期」这种能靠手动停用绕过的场景 |
| 桌面端检索/筛选页 | 桌面是配套端，只有一张裸表也能用 |
| 预算月份切换 | 中等收益，可以等 13 之后再说 |
| 桌面端深色模式 | 只改文档（第 8 点）；写第二套桌面样式表的收益远低于手机 |
| 流水分页 | 个人规模下（一年几千条）全表扫是毫秒级；真正会先崩的是第 6 点的全量上传 |
| 应用锁（生物识别/PIN） | 系统锁屏已覆盖「别人拿到我手机」这个威胁，两端各做一套是纯成本 |
| 桌面端账户类型下拉框 | `type` 字段在报表、预算、同步里都没有消费方，给没人读的字段做输入控件 |
| 自定义日期区间筛选 | 预设已覆盖绝大多数场景；代码注释里原本也记着「需要精确区间时再加」 |

## 构建环境备忘

本机做过一次完整出包，这几点会让下一个人少踩坑：

- `android/app/build` 与 `desktop/target` 里可能残留完整性级别更高的旧产物，当前会话的进程既写不进也删不掉，
  原地构建会直接失败在写文件上。临时办法是用 Gradle init script 把 `buildDirectory` 指到新目录；
  正式办法是在普通权限的终端里删掉这两个目录重建。
- `jpackage` 用 `Files.isWritable()` 校验输出目录，在受限令牌下它对**所有**目录都返回 false，会直接拒绝打包；
  桌面端出包需要不受限地运行。
- `outputs/TerminalLedger` 若继承工作区的 Low 完整性标签，从该目录直接启动的 exe 会因为写不了用户目录而
  出现「本地库只读」。用资源管理器复制或从 zip 解压出来的文件不带这个标签；
  就地修复用 `icacls outputs\TerminalLedger /t /setintegritylevel M`。

## 附：清单之外顺手修的

- **环图相邻扇区撞色**（用户反馈的截图）：调色板只有 6 色，`index % 6` 让第 7 块（最小、最后一块）
  取回第 1 块（最大）的颜色，而环是首尾相接的 —— 「医疗」和「餐饮」两块酸橙绿正好并排。
  改动：`values/pie_palette.xml` 与 `values-night/pie_palette.xml` 补到 8 色并按「同色系不相邻」重排；
  新增 `ChartColors.pieColors(count)`，保证相邻扇区（含首尾）不同色，颜色不够时重复只落在不相邻的位置。
  验证：按同一算法模拟，旧实现在 7 块时撞色索引 `(6, 0)`，新实现在 2–12 块、深浅两套下均无相邻撞色。
- **环图配色重新设计**（用户反馈「颜色选得差，不适配设计风格」）：原先的调色板把界面里的语义色
  当分类色用了 —— 红色代表支出、绿色代表收入、灰色代表禁用/空值，压在扇区上既打架又显脏，
  而且 `#EDEDED` 这种浅灰落在 `#FAFAFA` 卡片上几乎看不见（「教育」那块发白就是这个原因）。
  改动：新增 `pie_1..pie_8` 一组低饱和同伴色相（浅色在 `values/colors.xml`，深色在
  `values-night/colors.xml`，同一顺序、深色整体提亮降饱和），品牌绿只留给最大的一块；
  `pie_palette.xml` 改为引用这 8 个 token；桌面端 `app.css` 的 8 个 `default-color` 同步成同一套。
  验证：脚本直接解析两个 `colors.xml` 的实际色值，2–12 个分类、深浅两套都是「无相邻撞色」，
  桌面端 CSS 与手机端浅色逐色一致。候选方案对照图见 `docs/chart-palette-preview.png`。
- **环外引线穿过别的标签文字**（用户反馈的截图）：每条环外标签按**自己**纵向范围里环的外沿
  算折点 x，于是同一侧的各条竖段落在不同的 x 上 —— 靠圆心高度的那条被推到更外，另一条文字却
  更靠内，前者的竖段正好横穿后者的字（截图里「43元」被一条竖线穿过）。
  改动：新增 `computeCorridors`，**同一侧只留一条引线走廊**，文字一律在走廊外侧；
  引线改为「扇区 → 文字那一行」的单段斜线 + 一小段横线，不再有竖段。
  这样同侧引线按行序收敛、互不相交，也不可能压到任何文字。
  验证：按同样公式画了旧/新对照图（`docs/label-leader-preview.png`），旧做法里引线交叉、
  竖段落在文字范围内，新做法全部收敛到一条走廊、无交叉。真机渲染仍需装上确认。
- **桌面端饼图超过 8 个分类仍会绕回**：JavaFX 只循环 `default-color0..7`，类目超过 8 个时
  第 9 块会和第 1 块同色（手机端由 `ChartColors.pieColors` 处理了这个情况）。本次未改。

### 手机端按钮行高不齐（用户反馈的截图）

- **现象**：记账页「语音输入 / 截图记账 / 保存 / 模板」四个按钮一高一矮，文字基线也对不上；
  「语音输入」「截图记账」还被挤成两行。
- **原因**：同一行里混了两种 Material 按钮样式。`Widget.MaterialComponents.Button`（填充）
  默认带 `insetTop/Bottom = 6dp`，描边按钮是 0dp，于是同样的视图高度里，填充按钮的背景被收缩成
  36dp、描边按钮画满 48dp，看起来就是一个框高一个框矮。再加上四个 1:1 权重让「语音输入」这类
  四字标签放不下，换行后更高。
- **改动**：`fragment_record.xml` 四个按钮统一 `minHeight=44dp`、`insetTop/Bottom=0dp`、
  `maxLines=1`、`textSize=13sp`、等宽字体，行容器加 `baselineAligned="false"`；
  权重改成长标签 3、短标签 2（3/3/2/2），四字标签不再换行。
- **顺带修掉同类问题**：`fragment_report.xml` 的「AI 消费分析 / 设置」也是填充 + 描边混排
  （脚本扫全部 layout 找出来的），同样统一 inset 与 minHeight。其余页面要么整行描边、
  要么整行填充，不受影响。
- **为什么手机上没变化**：第一版仍用 versionCode 7 重新出包，和手机上已装的那个版本号完全相同，
  安装器不把它当更新，装上去也不会变。versionCode 提到 8 后才一定会覆盖安装。
  设置页本来就显示「版本 + versionCode + 构建时间 + 提交号」，装完后可以直接核对。
- **验证（在模拟器上真跑出来的坐标，不是纸面推算）**：装 b8 后 `uiautomator dump` 读控件边界：

  | 按钮 | x 范围 | y 范围 | 宽 | 高 |
  | --- | --- | --- | --- | --- |
  | 语音输入 | 28–587 | 580–657 | 559 | 77 |
  | 截图记账 | 587–1146 | 580–657 | 559 | 77 |
  | 保存 | 1146–1519 | 580–657 | 373 | 77 |
  | 模板 | 1519–1892 | 580–657 | 373 | 77 |

  四个 `y` 起止完全相同（580–657，高 77px，密度 280 下正好 44dp），宽度按 3:3:2:2 排开，
  28→1892 无缝铺满，说明之前「一高一矮」的 inset 差异已经被抹平。
- **窄屏没能在这个模拟器上验证**：模拟器把 app 跑在副屏的自由窗口里，`wm size 720x1280`
  只裁了截取范围，窗口没有重新测量（导出的坐标仍是 1920 宽时的布局，末尾按钮被裁掉）。
  真机竖屏下可用宽度约 360dp，按 3/10 与 2/10 分，四字标签分到约 106dp，
  13sp 四个汉字约 52dp，加上 Material 按钮默认左右 padding 仍放得下，不会折行。

### 记账日期可选（用户反馈：补记会落到第二天）

- **问题**：前一天忘记、第二天补记，`RecordFragment` 保存时硬写 `LocalDate.now()`，这笔就落到第二天。
  总账金额不变，但日均和标准差会算歪——统计是按日聚合的。
- **改动**：`fragment_record.xml` 的 `date_view` 从纯展示变成可点；`RecordFragment` 新增 `selectedDate` 字段、
  `pickDate()`（`DatePickerDialog`，`setMaxDate(now)` 禁止选到未来）和 `refreshDateLabel()`。
  保存时 `t.date` 优先用编辑态原日期，否则用 `selectedDate`；进编辑态时把这条的日期填回 `selectedDate`；
  保存完/退出编辑都重置回今天。
- **标签**：`今天 · 2026-10-24 ▾`、`昨天 · 2026-10-23 ▾`，其他日期直接显示 `2026-10-20 ▾`，末尾箭头提示可点。
- **验证**：`BUILD SUCCESSFUL`，aapt 复核 `versionCode='9' versionName='1.3.0'`；
  解包 `classes*.dex` 按字节搜索确认 `DatePickerDialog`（6 次）、`今天 · `、`昨天 · `、` ▾` 都在包里，
  说明新代码确实打进去了。装到模拟器上跑因 adb 反复掉线未完成，真机点开日期行确认即可。

### 报表页顶部数字不跟月份（用户反馈）

- **问题**：点跨月趋势的柱子只让环形图换了月份，`ReportFragment.renderSummary` 里仍写死
  `LocalDate.now()`，所以「本月收入/本月支出/结余」永远是当月；标题还写着「本月」，数字却是别的月。
  和桌面端仪表盘那个问题同源。
- **改动**：`renderSummary` 改成跟 `pieMonth` 走——三个数字、环比（改为对选中月的上一个月）、
  以及三个标题文字都跟着换（本月 → `9月`）。净资产仍是全期口径（含账户初始余额），不跟月份。
  `fragment_report.xml` 给三个标题加 `caption_income / caption_expense / caption_balance`；
  `selectTrendMonth` 和统计范围切换两处都补了 `renderSummary` 调用。
- **验证**：`BUILD SUCCESSFUL`，aapt 复核 `versionCode='10' versionName='1.3.0'`；
  dex 里 `本月` 出现 9 次、`结余` 2 次，`R.id.caption_*` 能被编译通过即证明三个 id 已进资源表。

### 「AI 设置」弹窗不能滚动（用户反馈）

- **问题**：`AiSettingsDialog` 两个弹窗都用 `LinearLayout` 直接 `setView`。AI 设置那个还把一大段说明文字
  交给 `setMessage`，`AlertDialog` 只把 message 放进内部滚动区，自定义表单排在它下面且自己不滚，
  小屏上「接口地址 / 模型」输入框被推出屏幕，够不到也拖不动。
- **改动**：说明文字改成一个 `TextView` 和三个输入框一起放进同一个 `LinearLayout`，整体再包进
  `ScrollView`（提示词编辑弹窗同样处理），并去掉 `setMessage`。
- **验证**：`BUILD SUCCESSFUL`，aapt 复核 `versionCode='11' versionName='1.3.0'`。
  出包后按约定删掉 b10 两个文件，`outputs/apk` 只留 b11。

### 记完账切回报表页不刷新（用户反馈）

- **问题**：底部导航是 hide/show 模式，报表页常驻不重建，切回来只走 `onHiddenChanged`。
  那里当时只调 `replayChartAnimations()` 重绘三张图（为了让生长动画重播），
  顶部「收入 / 支出 / 结余」、预算卡片、热力图都没有重算 —— 刚记的那笔在记账页和流水页都有，
  报表页纹丝不动。
- **改动**：`replayChartAnimations` 换成 `refreshOnReturn`，依次重算
  `renderSummary / renderBudget / renderHeatmap / renderPie / renderMonthTrend / renderTrend`，
  整页按最新数据刷新，图表顺带把生长动画再播一遍。
- **验证**：`BUILD SUCCESSFUL`，aapt 复核 `versionCode='12' versionName='1.3.0'`。
  出包后按约定删掉 b11 两个文件。
  真机操作：记一笔收入 → 切到报表页，顶部收入应立刻加上这笔的金额。

### 套用模板后分类丢失（用户反馈）

- **问题**：模板本身存了 `categoryClientId`（模型、表、同步载荷都有这一列），
  但套用后分类永远是空的，还得手选一次。根因在 `buildCategoryBar()` 第一行
  `selectedCategoryId = null;` —— 它是为「切换收入/支出后必须重选分类」写的，
  而 `applyTemplate` 的顺序是「先设分类 → 再调用 `buildCategoryBar()` 重建分类栏」，
  刚设好的分类立刻被抹掉。
- **改动**：改成「只有当当前选中的分类不在这次要显示的列表里时才清空」。
  切收入/支出时它自然不在列表里，行为不变；套用模板时分类能保住。
  末尾补一句 `if (selectedCategoryId != null) selectCategory(selectedCategoryId);`，
  把高亮也补回来。
- **验证**：`BUILD SUCCESSFUL`，aapt 复核 `versionCode='13' versionName='1.3.0'`。
  出包后按约定删掉 b12 两个文件。
  真机：点「模板」→ 选一个套用，分类栏应该直接高亮模板里的那个分类，不用再选。
