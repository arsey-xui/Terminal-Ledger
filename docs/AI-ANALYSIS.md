# AI 消费分析与截图识别

> 范围包含两块：**报表层**生成自然语言消费解读；**截图记账**做字段提取（金额 / 账户 / 分类）。
> 仍然**不**自动同步银行账单。

## 设计目标

- 离线时可用：内置**规则引擎**，无外部依赖。
- 配置后可用大模型增强：留出占位接口，可从 OpenAI 兼容接口切换到任意模型。

public interface AiReportService {

## 规则引擎（默认）

输入：本月支出/收入/结余、环比、分类 Top、预算预警、**按天统计的日平均支出 / 日支出标准差 / 日支出中位数**。输出一句话/几句话的解读，例如：

> 本月总支出 1500.00 元，较上月上涨 15.0%，注意控制开销。支出最多的是「餐饮」。【接近预算】购物（92%）。本月 30 天共支出 1500.00 元，日平均支出 50.00 元，日支出标准差 62.15 元，日支出中位数 25.00 元。日均明显高于中位数，说明少数几天花得多，把平均值拉高了。

### 三个统计量的口径（按天，不是按笔）

先把逐笔流水**按日期汇总成「每天花了多少」**，再对每日金额算统计量 —— 所以「平均」是**日平均**，
不是每笔的平均。两者差别很大：一天买三次菜在按笔口径里是三个样本，在按天口径里只是当天的一笔汇总。

三端（后端 `service/ai/ExpenseStats`、电脑端与手机端 `analysis/ExpenseStats`）是同一套算法，
用 `BigDecimal` 而不是 `double`，保证同一个月的数字在哪一端看都一样。

| 指标 | 算法 | 说明 |
| --- | --- | --- |
| 日平均支出 | 总支出 ÷ **统计天数** | 分母是「1 号到今天」的自然天数，**没花钱的日子按 0 参与**。收入不参与 |
| 日支出标准差 | 样本标准差（除以 n-1） | 把每天金额当样本，衡量「每天的花费起伏多大」；只有 1 天时无定义，按 0 处理并在文案里注明 |
| 日支出中位数 | 排序后取中间；偶数天取中间两天均值 | 只要一半以上的日子没花钱，中位数必然是 0，这时文案会说「半数以上的日子没有支出」 |

**为什么没花钱的日子也要算一天**：这是记账里的常规读法（「这个月平均每天花多少」），
也让月末和月初可比。只统计有支出的日子会让日平均系统性偏高 —— 月末那几天买菜的次数多，
按笔算会把总额摊成很多个小样本，按天算才看得出「这几天一天花了多少」。
查看已结束的月份时按整月天数算；查看当月时算到**今天**为止。

文案里还会带一句算术结论：**只有日均与中位数差距超过 1.5 倍（或低于 0.5 倍）时才下判断**，
说「少数几天花得多，把平均值拉高了」（日均 > 中位数）或「有一半以上的日子花费都在中位数以上」（日均 < 中位数）；
差距不到这个量级就说「每天的支出比较均匀」。阈值取 1.5 倍而不是小容差，是因为日均与中位数天然就会有些许差异，
把这种正常差距说成「被大额拉高」等于给用户一个错误结论。当月没有支出记录时，只输出一句中性说明，
不输出会误导的 0.00。

## 大模型占位接口

```java
public interface LlmClient {
    String complete(String system, String user);
}
```

- 配置 `AI_API_KEY`、`AI_MODEL`、`AI_BASE_URL` 后，`AiReportServiceImpl` 会把结构化报表数据拼成上下文，调用 `LlmClient`。
- 未配置或调用失败时，自动回退到规则引擎。

## 自定义提示词

分析口径写死在提示词里，用户想换侧重点（例如「只讲三句」「按 Necessity/Want 分类」「用英文回答」）
不必改代码：两端「AI 设置」里都有一个「分析提示词」入口。

| 端 | 入口 | 存放位置 |
| --- | --- | --- |
| 手机端 | 报表页「AI 设置」→「分析提示词」（或设置页进入的同一个弹窗） | `SharedPreferences` 的 `ai_prefs/ai_prompt`（明文，不是机密） |
| 电脑端 | 左栏「AI 设置」→「分析提示词」输入框 | `~/accounting/ai.properties` 的 `promptB64`（Base64(UTF-8)，避开 properties 的换行续行与冒号分隔规则） |
| 后端 | `POST /api/report/ai` 的 `prompt` 字段 | 不落盘，按请求生效 |

- **留空即用默认提示词**，默认那份就是代码里的 `DEFAULT_PROMPT`（`AiReportServiceImpl.DEFAULT_SYSTEM_PROMPT`、
  电脑端 `AiReportGenerator.DEFAULT_PROMPT`、手机端 `AiAnalysis.DEFAULT_PROMPT`，三处文本一致）。
- 弹窗里都有「恢复默认提示词」，一键填回默认文案。
- 自定义提示词**只影响报表层分析**：截图识别的提示词是固定输出契约（只准输出 JSON），
  改掉会直接解析失败，所以两者刻意分开。
- 手机端提示词是明文存的：它不像 API Key 那样是凭证，而且用户要能随时打开看见、改回去。
- 提示词与 API Key 是同一份配置文件但独立字段：切回规则引擎不会丢掉写好的提示词。

### 输入给大模型的内容

规则引擎生成的正文本身就是大模型的上下文（`user` 消息），里面已经算好日平均 / 日支出标准差 / 日支出中位数，
模型不需要自己做算术。系统提示词（默认那份）要求模型把这三个数纳入分析。

## 截图记账的字段识别（多模态）

两条并行的路，按用户是否配置 API Key 自动选择：

| 路径 | 何时使用 | 做法 |
| --- | --- | --- |
| 本机离线 | 没配 API Key | ML Kit 端上中文 OCR → `BillTextParser` 规则解析金额与商户；分类按商户名猜，账户由用户选 |
| AI 多模态 | 配了 API Key | 截图整张交给多模态模型，一次拿到金额 / 类型 / 账户 / 分类 / 商户 / 日期 |

AI 那条路的任何失败（网络不通、模型不支持图像、返回解析不出）都会**自动回退**到本机离线那条，
所以这个功能不会因为没网或没配 Key 而不能用。

### 提示词

系统提示（`BillAiPrompt.SYSTEM`）规定输出格式与判断规则；用户消息里带上**用户自己的**账户与分类列表，
要求模型只能从列表里原样选、选不出填 null —— 这样不会出现模型自己编一个分类名的情况。

```text
你是记账 App 的截图识别器：看图，提取一笔账的字段。

【输出】只输出一个 JSON 对象，不要解释、不要 Markdown 代码块、不要多余文字：
{"amount":数字,"type":"EXPENSE"或"INCOME","account":字符串或null,"category":字符串或null,"merchant":字符串或null,"date":"yyyy-MM-dd"或null}

【字段】
- amount：这笔账的实际金额，正数，不带货币符号。取「实付 / 付款金额 / 交易金额 / 订单金额 / 合计」
  这类明确写着消费金额的那个数。
- type：支出填 "EXPENSE"；退款、收款、别人转给你填 "INCOME"。
- account：付款方式，必须从用户给的「账户列表」里原样选一个；判断不出填 null。
- category：消费分类，必须从用户给的「分类列表」里原样选一个；判断不出填 null。
- merchant：商户名或对方名称，用于备注；没有填 null。
- date：交易日期；截图里没有或看不清填 null。

【必须避免】
1. 不要把余额、零钱、优惠、折扣、立减、积分、手续费、额度、订单号、单号、时间、卡号尾号当成 amount。
2. 截图里通常有很多数字，只取「这次实际支付」的那一个；金额前带减号（-27.50）仍然填正数。
3. account 和 category 如果列表里没有合适的，就填 null，不要自己编一个名字。
4. 任何字段拿不准就填 null，不要猜。

【示例】看到「星巴克 实付 ¥27.50」这类内容时输出：
{"amount":27.5,"type":"EXPENSE","account":"支付宝","category":"餐饮","merchant":"星巴克","date":null}
```

用户消息（`BillAiPrompt.userText`）+ 图片：

```text
账户列表：现金、储蓄卡、信用卡、微信、支付宝
分类列表：餐饮、交通、购物、住房、通讯、医疗、教育、娱乐、人情、其他

请识别下面这张支付/账单截图，按系统提示的格式只输出 JSON。
```

要点：

- **输出契约**：只输出一个 JSON 对象。解析端仍然容忍 ```json 代码块和前后多余的解释文字
  （`BillAiPrompt.firstJsonObject` 按括号配对截取，字符串里的括号与转义不会干扰）。
- **金额最容易错**：账单页上余额、优惠、立减、积分、订单号都长得像金额，所以单独一段「必须避免」把它们列全。
- **拿不准就 null**：列表里没有合适的就留空，界面保持原值让用户自己补。
- 模型返回的账户/分类还会在本地**再校验一次**（必须命中本机列表），编造出来的名字直接丢弃。

### 字段落地

金额写进输入框、分类走 `matchCategory()` 预选、账户切到识别到的那个；识别为收入（退款、收款）时
**先切收支开关再选分类**（收支两套分类是分开的，切换会重建分类栏）。预选之后照旧弹出确认框，用户随时可改。

### 图片与成本

截图先缩到长边 1568px 再转 JPEG（质量 85）后 base64 内联，避免把原图几 MB 直接塞进请求；
再大对识别金额也没有帮助，只会更慢更贵。

### 常见服务怎么填

「AI 设置」里要填三项：**接口地址、模型、API Key**。截图识别要求模型**支持图像输入**，
报表分析只要求文本能力；选一个两者都支持的模型，一份配置就能覆盖两个功能。

| 服务 | 接口地址 | 模型 | 截图识别 |
| --- | --- | --- | --- |
| OpenAI | `https://api.openai.com/v1` | `gpt-4o-mini` | 支持 |
| DeepSeek | `https://api.deepseek.com` | `deepseek-flash` | 支持（文档里 Vision 为 ✓） |
| DeepSeek | `https://api.deepseek.com` | `deepseek-v4-pro` | 不支持图像，截图会回退本机识别 |

- 接口地址**不用**带 `/chat/completions`，代码会自己拼上；也不用带 `/v1`（文档给的就是不带 v1 的形式）。
- DeepSeek 建议用 `deepseek-flash`。旧名 `deepseek-v4-flash`、`deepseek-v4-flash-vision-exp`
  仍可调用，但对应模型已下线，请求会由 DeepSeek-V4.1-Flash 承接。
- DeepSeek 的思考模式**默认开启**（effort 默认 high），思维链与最终回答共享输出预算，
  所以客户端**不设置 `max_tokens`** —— 设小上限会让思维链占满预算、`content` 返回空，
  每次都会白白回退到本机识别。思考模式下 `temperature` 会被忽略（不报错，也不生效），
  非思考模型仍然生效。
- 思考模式会让每次识别慢一些（客户端读超时给了 120s），但对着模糊账单通常更准。

## 安全与隐私

- **API Key 是本机配置，不参与同步，也不发给后端。** 同步载荷（`SyncPayloads`）只有流水、分类、
  账户、预算、模板、周期规则，没有任何 AI 配置字段；手机端调用模型时是**直连**用户填的那个接口地址
  （`AiAnalysis.LlmClient`、`BillAiRecognizer`），不经过本项目服务器。因此换设备要各自填一次 Key。
  （`AiPayloads` 那个「客户端自传 Key 给后端」的传输对象目前**没有任何调用方**；真要启用，
  等于把用户的钱包凭证交给后端和数据库，需要同步评估传输与落盘加密。）
- 报表分析只上传**汇总后的数据**（金额、分类聚合、预算比例），不上传全量流水明细。
- 截图识别会把用户选中的**整张截图**上传到**用户自己填写的**接口地址，手机直连该地址，
  不经过本项目的任何中转。不想上传就不要配 API Key，本机离线识别始终可用。
- **手机端 API Key 是加密存放的**：用 Android Keystore 里的一把 AES-256-GCM 密钥加密后才写进
  `SharedPreferences`（`ai_prefs`）。Keystore 密钥不可导出，支持 TEE / StrongBox 的机型上不出安全硬件，
  所以整个 `/data` 被读走、或备份恢复到另一台设备，都解不开那段密文。
  旧版本留下的明文会在下次保存时自动换成密文；Android 6.0（API 23）以下没有 Keystore AES，
  退回明文存储；解不开时（换设备、密钥失效）清掉并让用户重填，不会崩。
- **电脑端仍是明文**（`~/accounting/ai.properties`）：纯 Java 没有可用的系统密钥库，
  除非引入 JNA 调 Windows DPAPI 这类本地依赖。该文件位于用户自己的目录下，
  实际暴露面限于「以该用户身份运行的程序」。
- 后端侧的 Key 通过环境变量 `AI_API_KEY` 注入，`application.yml` 中为占位符。
